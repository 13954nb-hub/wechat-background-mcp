# Capabilities and boundaries (2.5.2)
## 简体中文摘要

这是仅供本机使用的实验性 MCP 服务，登记 29 个工具；目录数量不代表所有功能都经过实机端到端验收。仅支持 Windows x64、CPython 3.12 x64，以及完整 DLL 指纹匹配的微信 Windows 4.1.13.12。UI 操作须与微信位于同一交互桌面，并在每次操作时重新检查控件和窗口几何；不要求固定显示器分辨率，也不能复用固定坐标。多会话监听是客户端驱动的有界轮询，每次 1–60 秒、默认检测间隔 5 秒，最多 16 个选定会话；服务端不会常驻监听或自动生成回复。只有发话者身份有充分证据时才标记 self／other；未知方向须暂停。原生 @提及及不支持的附件查看通过 Computer Use 交接，不由 MCP 自行点击或发送。请查看[双语工具目录](docs/TOOLS_AND_WORKFLOWS.md)、[简体中文首次部署](docs/zh-CN/快速开始.md)、[English first deployment](docs/en/GETTING_STARTED.md)和[双语免责声明](DISCLAIMER.md)。

The server registers **29 MCP tools**. They cover status/capability reporting; bounded visible and authenticated local conversation reads; selected-chat polling; contact and message reads; bounded UI navigation; conversation, group-candidate and message search; already-downloaded attachment access; and guarded local text, image and small-file submission. `wechat_capabilities` reports the runtime's detailed limits.

## Supported environment

- Windows x64, an existing logged-in Weixin **4.1.13.12** client, and the exact pinned DLL hash and size.
- The same persistent `WXBG_STATE_DIR` for every MCP client pointed at this installation.
- UI tools require a minimized main window, no competing Weixin popup, and current accessibility/layout evidence for each action. A native click is permitted only when its live semantic target and render-client geometry are verified.
- Every guarded MCP read and UI action first enumerates the main window on the MCP process's interactive Windows desktop. A Computer Use controller can see a different desktop. A visible Weixin window in its screenshot does not establish MCP access; `TARGET_NOT_VISIBLE` blocks database reads too.

`wechat_status.layout_calibration` makes a first measurement of this computer's Weixin root rectangle, render client, observable controls, and operation readiness. Status does not navigate, send, or edit drafts, but it may briefly lease and restore the version-pinned in-process access gate; require `cleanup.restored=true` and no cleanup errors. Monitor resolution is not the Weixin window rectangle. UI actions derive their own coordinates from fresh, action-specific semantic controls and recheck the window, target and draft before input; missing, ambiguous, clipped or changing evidence fails closed. Resizing, DPI changes or a different desktop require a new `wechat_status` observation, but the initial report is not a permanent coordinate cache or a guarantee that all 29 tools are ready. The read-store decoder accepts a zero-page-size WAL index only when frame and page counts are both zero and its other checks pass; other invalid indexes remain rejected.

## Search and identity

- `wechat_search(scope="conversations")` searches bounded nonhidden SessionTable candidates.
- `wechat_search(scope="groups")` searches fresh authenticated contact-only candidates first, then SessionTable rows including hidden ones. It returns only keys ending in `@chatroom`, marks each row with `candidate_source: contact|session`, and marks every item and result `membership_unverified: true`. Neither source establishes current membership, exhaustive group coverage, or permission to send.
- `wechat_search(scope="messages")` searches supported text in one exact database conversation. Unsupported bodies remain unavailable.
- Search is literal Unicode casefold matching, at most 500 scanned rows per call. Group pages use `username` ascending within each source, so new messages do not reorder unvisited candidates. `has_more` means scanning remains, even if no item matched on that page. Restart with no cursor when group membership or names may have changed. Pages are not one atomic roster snapshot.
- Database `conversation_key` values cannot be passed as UI `session_ref` values. Verify a unique current UI identity before actions that open or send.

## Hybrid MCP and Computer Use

The server advertises the discoverable `wechat_hybrid_computer_use` MCP prompt. It gives agents a handoff checklist: use bounded authenticated MCP reads only when the same-desktop main-window check passes, and use a Computer Use controller only on the desktop containing Weixin for GUI actions. `TARGET_NOT_VISIBLE` blocks MCP reads and UI actions alike. `readstore_index_invalid` means the database index snapshot was rejected; stop database reads and use a supported UI observation only if its checks pass. Never reconstruct a WAL index or change Weixin's database sidecars. Do not issue MCP UI and Computer Use input concurrently. The two controllers' observations are separate; recheck the selected group and draft in the actual Weixin UI before acting.

If the offscreen session container probe reports that it cannot address a row, a capable Computer Use client may locate that row in the live UI after checking the current desktop and account. A `wechat_wait_for_ui_hint` timeout is not proof that no message arrived; use the bounded database watch or a separately verified UI observation. Never switch controllers to resend a mutation with `outcome_unknown`.

`wechat_send_at_username` returns a structured **Computer Use handoff**, never a send. Its `sent` and `dispatch_performed` fields are `false`; the server neither calls a host Computer Use controller nor creates a send Journal entry. The required `username` and optional `session_ref`, conversation title/key, and operation ID are caller supplied, unverified hints. An MCP client with Computer Use support must operate the desktop containing Weixin, identify the live group and exact member suggestion, select that suggestion, then observe both the intended native mention token and complete unsent draft before one explicitly authorized Send action. A contact remark and group nickname can differ; spelling similarity alone does not establish identity. Do not use Down or Enter to navigate the mention popup: those keys may enter text or send the message. If Computer Use is unavailable or identity is ambiguous, stop. A wrong draft remains unsent; an accidental local send or `outcome_unknown` must be reported without silent retry or remote-delivery claims.

## Selected-chat monitoring

`wechat_watch_new_messages` makes one bounded long-poll call over 1–16 selected conversations. Before starting, the AI client uses a total monitoring duration already given by the user in seconds or minutes, or asks once if it was omitted; it does not assume a total duration. First obtain `account_epoch` and a `start_from="now"` cursor for one room with `wechat_read_new_messages`; use that epoch with `wechat_batch_read_messages` to initialize the remaining selected rooms from now. Each watch room requires its retained cursor. Each call supplies an integer `wait_seconds` from 1 to 60. The watch returns the latest cursor for every room on activity, backlog, a detected gap, or after the requested call window; one bounded read may extend total wall time. The user may set the target detection interval to 1–60 seconds (`poll_interval_ms=1000–60000`); when omitted, it defaults to 5 seconds (5000 ms). A read may take longer than the target interval. The read mutex is released between polls. It does not stay active after the tool returns. The active AI client retains each room's returned cursor and repeats bounded calls until the user's total duration has elapsed; `wechat_multi_chat_reply_loop` describes that workflow.

The same client-side total duration rule applies to `wechat_wait_for_ui_hint`. Each call supplies an integer `timeout_seconds` from 1 to 60; a longer user-requested duration requires repeated bounded calls by an active client. This event wait has no detection-interval setting. Its result is a generic UI activity hint, not a verified incoming message. A timeout is not proof that no message arrived; verify with database cursors or a separate live UI observation.

Message results use `sender_role` (`self`, `other`, `unknown`), `sender_role_verified`, and `sender_role_evidence`. The evidence enum is `database_account_match`, `database_direct_contact_match`, `database_group_member_match`, `live_ui_sender_side`, `local_outgoing_operation`, `ambiguous`, or `unavailable`. Database rows map each shard-local `sender_id` only through that same shard's `Name2Id.rowid`, then compare exact usernames with the authenticated account or exact conversation key. Group members require a complete bounded `chat_room` → `chatroom_member` → `contact` join from the same contact-store snapshot. Only these exact matches produce verified database roles. Unsupported schema, absent/incomplete roster, ambiguous identities, and unmapped IDs remain `unknown`. Only the currently exposed rows from `wechat_read_messages` use visible UI direction, based on a unique nested text element's position in the current message frame; missing, clipped, ambiguous, middle-position, or changed geometry returns unknown. UI observations cannot promote database watch rows by matching text, time, or position. Only `sender_role="other"` with `sender_role_verified=true` may enter an automatic-reply candidate set; ignore verified self and pause that room on unknown. Successful MCP text/file/image sends expose `self`, `true`, `local_outgoing_operation` for the local operation only; a send result is not a database message identity or remote receipt. A database `conversation_key` is not a sendable `session_ref`. A room-specific gap, identity, or send uncertainty also pauses that room. A batch-level read/cursor error pauses the affected batch until separate read-only checks isolate valid rooms. The server itself performs no AI generation or automatic reply; polling latency, full coverage, and exactly-once processing are not guaranteed.

## Image and file view fallback

`wechat_get_attachment` takes an exact database message identity and privately searches the account's downloaded `msg\attach\<chat MD5>\<YYYY-MM>\Img\<locator>.dat` or `_h.dat` cache candidates. For an image, it decodes the container, matches the declared message size and MD5, and accepts supported static PNG, JPEG, or WebP bytes. The encrypted cache path is not exposed as an image path. Verified images up to 4 MiB (4,194,304 bytes) are returned as inline MCP `ImageContent` as well as a temporary resource link; `result.inline_image_available` reports whether the inline block is present. Larger verified images and supported files keep the resource link without inline image content. The AI client must have image vision to recognize content; the MCP server itself performs no OCR or image recognition. It also cannot prove sender direction from image bytes or the numeric database sender ID. Before an automatic reply, confirm the exact live UI message came from the other person and belongs to the selected chat.

`wechat_read_file_card` observes only file-card state, not file contents. If a client cannot consume the inline image or resource, or an exact attachment is unavailable or unsupported, `wechat_view_attachment_handoff` returns `viewed: false`, `dispatch_performed: false`, and unverified hints for a capable Computer Use client. The client must locate the exact chat and message on the live Weixin desktop and inspect only a supported in-app preview. It must stop on account change, ambiguous identity, or file/path change; it cannot treat a visual preview as validated original bytes or execute a file/macro. The MCP server cannot call Computer Use itself. Unsupported animated formats and content that was never downloaded remain outside this byte path.

## Important exclusions

No complete chat-history guarantee, full contact-directory guarantee, remote message-delivery receipt, native `@` mention token, quote reply, payments, red packets, transfers, calls, Moments, account changes, or autonomous continuous message listener. MCP attachment byte access is limited to already-downloaded verified resources. The installed tool count does not mean all 29 tools have been verified end to end on arbitrary customer machines.

All unknown outcomes remain unknown and are never automatically retried. For exact per-tool limits, use the server's `wechat_capabilities` response.
